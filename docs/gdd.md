# เอกสารการออกแบบเกม: Summer Camp Romance (ชื่อชั่วคราว)
*(Game Design Document - GDD)*

---

## 1. ภาพรวมโครงการ (Overview)
* **ชื่อโปรเจกต์:** Summer Camp Romance (Working Title)
* **ประเภทเกม (Genre):** Interactive Drama / Romance / Dating Sim
* **แพลตฟอร์ม (Platform):** PC (Windows / macOS / Linux ผ่าน Tauri) และ Web (สำหรับเปิดเดโมบนเบราว์เซอร์)
* **ชุดเทคโนโลยี (Tech Stack):** React 19 + TypeScript + PixiJS v8 (WebGPU พร้อม WebGL Fallback) + Tauri v2 (Rust Backend สำหรับ Native File I/O)
* **ระดับความเหมาะสมและเรตติ้ง (Rating & Tone):** **18+ / Adult Romance** (เน้นเสน่ห์ทางกายภาพ สรีระ ภาษากาย ความสัมพันธ์ลึกซึ้ง และความตึงเครียดเชิงโรแมนติกแบบผู้ใหญ่ โดยไม่มีภาพลามกอนาจารแบบฮาร์ดคอร์)
* **กลุ่มเป้าหมาย (Target Audience):** ผู้เล่นวัยผู้ใหญ่ (18+) ที่ชื่นชอบเกมนิยายเชิงโต้ตอบแนว LGBTQ+, ซีรีส์ดราม่าความสัมพันธ์ และเกมโรแมนติกที่เน้นมิติทางอารมณ์และจิตวิทยา
* **อายุและสถานะตัวละคร:** ตัวละครโรแมนติกและตัวเอกทุกคนมีอายุ 18 ปีขึ้นไป (Young Adults) โดยค่ายนี้เป็นรีทรีตกิจกรรมฤดูร้อนสำหรับผู้ใหญ่ (Adult Summer Retreat)
* **Elevator Pitch:** เกมโรแมนติกค่ายฤดูร้อน 5 วันที่คุณจะได้รับบทเป็นผู้เข้าร่วมค่ายหน้าใหม่ที่ต้องบริหารเสน่ห์ ความปรารถนา การแข่งขัน และความลับท่ามกลางกลุ่มเพื่อนสนิท 3 หนุ่มที่มีประวัติผูกพันกันมาก่อน
* **แก่นความรู้สึกหลัก (Core Fantasy):** ดื่มด่ำกับบรรยากาศฤดูร้อน แสงแดด และความเย้ายวนของหนุ่มนักกีฬา มีอิสระในการหยอด หว่านเสน่ห์ สับราง หรือสร้างความผูกพันที่จริงใจ พร้อมลุ้นระทึกกับดราม่าความหึงหวงและผลลัพธ์ของการกระทำในค่ำคืนสุดท้าย

## 2. เสาหลักการออกแบบ (Design Pillars)
1. **เครือข่ายความสัมพันธ์ที่มีชีวิต (Dynamic Social Web):** ตัวละครเป้าหมายทั้ง 3 คนรู้จักกันมาก่อน มีความผูกพันและการแข่งขันกันเอง การเข้าหาตัวละครหนึ่งจะส่งแรงกระเพื่อมไปยังคนอื่นเสมอ ไม่ใช่การจีบแยกห้องเดี่ยว
2. **เนื้อเรื่องบรรจบตาม State (State-Driven Narrative Convergence):** หลีกเลี่ยงการแตกกิ่งก้านสาขาจนบานปลาย ฉากทั้ง 24 ฉากดำเนินไปตามแกนเรื่องหลักร่วมกัน แต่บทสนทนา ท่าที สายตา และความใกล้ชิดจะเปลี่ยนไปตามค่าความสัมพันธ์และประวัติที่สะสมมา
3. **เสน่ห์ดึงดูดและบรรยากาศโรแมนติกวาบหวาม (Sensual Appeal & Romantic Tension):** ขับเน้นเสน่ห์ทางกายภาพ สรีระ ภาษากาย การสบตา และโมเมนต์ใกล้ชิดสองต่อสองตามมาตรฐาน **18+ / Adult Romance**
4. **ผลลัพธ์ที่เกิดจากพฤติกรรมจริง (Consequences Over Stat Grinding):** เน้นความเชื่อใจและความจริงใจ การโกหกหรือสับรางจะถูกจดจำผ่าน Flag และนำมาเปิดโปงในจุดสำคัญ มากกว่าแค่การบวกลบคะแนนตัวเลข

## 3. วงจรการเล่นหลัก (Core Gameplay Loop)

```
+----------------------------------------------------------------+
|                 การนำเสนอฉากแบบภาพยนตร์ (Cinematic VN)            |
|            (PixiJS v8 WebGPU Renderer + สไปรต์จัดวางไดนามิก)       |
+----------------------------------------------------------------+
                               |
                               v
+----------------------------------------------------------------+
|                       ทางเลือกของผู้เล่น (Choice)                 |
|       (เลือกโทนคำตอบ / เลือกร่วมกิจกรรม / เลือกความจริงหรือโกหก)      |
+----------------------------------------------------------------+
                               |
                               v
+----------------------------------------------------------------+
|                  อัปเดตสถานะความสัมพันธ์ (State Mutation)           |
|      - ปรับ Attraction (+/-)                                   |
|      - ปรับ Trust (+/-)                                        |
|      - บันทึกความทรงจำการโกหก ("lied_about_X = true")            |
|      - อัปเดต Relationship Status ตามเกณฑ์ที่กำหนด                  |
+----------------------------------------------------------------+
                               |
                               v
+----------------------------------------------------------------+
|              การตอบสนองทันทีและฉากถัดไป (Reaction & Resolution)    |
|   - สัญลักษณ์ความรู้สึกเล็กๆ (หัวใจ / รอยร้าว / สีหน้าตัวละคร)           |
|   - เข้าสู่ฉากหลักที่มีบทพูดเฉพาะกลุ่ม หรือ ปลดล็อก Mini-Event สองต่อสอง  |
|   - เดินทางสู่ฉากถัดไปตาม Choice Priority Routing                |
+----------------------------------------------------------------+
```

* **Micro Loop (ระดับฉาก, 2–5 นาที):** อ่านบทสนทนา → เลือกทางเลือก → สังเกตสีหน้าและปฏิกิริยาของตัวละครทันที → ปลดล็อกบทพูดหรือการแซวเฉพาะตัว
* **Meso Loop (ระดับตอน/Episode, 20–30 นาที):** เข้าร่วมกิจกรรมประจำวันของค่าย → สะสมเคมีและความลับ → สัมผัสการแข่งขันระหว่างหนุ่มๆ ในช่วงกลางวัน → แอบนัดพบกันช่วงกลางคืน
* **Macro Loop (ระดับจบเกม, 1.5–2.5 ชั่วโมง):** บริหารความสัมพันธ์ตลอด 5 วันผ่าน **24 ฉาก** → เผชิญหน้ากับความลับที่ถูกเปิดเผยในวันที่ 4 → สรุปบทลงเอยรอบกองไฟคืนวันที่ 5 สู่ 1 ใน 6 ฉากจบ

## 4. ประสบการณ์ของผู้เล่นตามช่วงเวลา (Player Experience)
* **Day 1 (แรกพบและหว่านเสน่ห์):** ก้าวเข้าสู่ค่ายในฐานะผู้เข้าร่วมใหม่ สัมผัสความตื่นเต้น เริ่มสำรวจเคมีของหนุ่มแต่ละคน และกำหนดบุคลิกเริ่มต้นของตัวเอก
* **Day 2–3 (แสงแดด เหงื่อ และการแข่งขัน):** กิจกรรมกีฬากลางแจ้ง ว่ายน้ำริมทะเลสาบ ฉากถอดเสื้อและการแข่งขันระหว่างเพื่อนเพื่อแย่งชิงความสนใจของตัวเอก
* **Day 4 (ค่ำคืนแห่งความลับและความเสี่ยง):** การแอบออกไปเจอกันหลังเคอร์ฟิว ความใกล้ชิดสองต่อสองที่ลึกซึ้งขึ้น การสับรางและข่าวลือที่เริ่มแพร่สะพัดในกลุ่ม
* **Day 5 (บทสรุปและการเคลียร์ใจ):** ค่ำคืนรอบกองไฟสุดท้าย การสารภาพความในใจ หรือการเผชิญหน้าเมื่อความจริงเรื่องการสับรางแตกออก นำไปสู่ความรู้สึกทางอารมณ์ที่ชัดเจน

## 5. ตัวละครเอก (Protagonist)
* **ตัวตน:** ชายหนุ่มวัยผู้ใหญ่ (Young Adult, 18+) ที่เพิ่งมาร่วมค่ายฤดูร้อนแห่งนี้เป็นปีแรก
* **การปรับแต่ง:** ผู้เล่นสามารถตั้งชื่อได้เอง
* **จุดเริ่มต้น:** เป็นคนนอกที่ไม่เคยรู้จัก 3 หนุ่มมาก่อน ทำให้ไม่มีแต้มต่อหรือปมในอดีต ผู้เล่นสามารถเริ่มต้นความสัมพันธ์จากศูนย์ไปพร้อมกับตัวละครได้ทันที
* **น้ำเสียงและบุคลิก:** มีพื้นฐานเป็นคนอัธยาศัยดี เอาตัวรอดเก่ง แต่ท่าทีและระดับการเปิดเผยเรื่องเพศสภาพจะขึ้นอยู่กับทางเลือกของผู้เล่น:
  * *สายรุก/หว่านเสน่ห์ (Bold & Flirty):* หยอดคำหวาน สบตาตรงๆ ไม่กลัวที่จะสัมผัสร่างกาย
  * *สายจริงใจ/อบอุ่น (Sincere & Grounded):* รับฟัง เปิดใจ พูดความจริง เป็นที่พึ่งทางใจ
  * *สายกวน/สงวนท่าที (Playful & Deflective):* แกล้งแซว กวนประสาท ไม่เปิดเผยความรู้สึกง่ายๆ สับรางเก่ง

## 6. ตัวละครเป้าหมายและเครือข่ายความสัมพันธ์ (Romance Characters & Social Web)
ตัวละครทุกคนมีอายุ 18 ปีขึ้นไป (Young Adults)

### ไดนามิกดั้งเดิมระหว่าง 3 หนุ่ม (Predefined Group Dynamics)
ทั้ง 3 คนรู้จักและมีความสัมพันธ์กันเองมาก่อนที่ตัวเอกจะเข้ามา:
* **Jake ↔ Ethan:** เพื่อนสนิทตั้งแต่วัยเด็กที่มีการแข่งขันกันเงียบๆ Jake เป็นผู้นำสายลุย ส่วน Ethan มักมองทะลุความโอ้อวดของ Jake
* **Jake ↔ Ryan:** คู่หูสายปาร์ตี้ ชอบกิจกรรมมันๆ กีฬา และการหยอกล้อกันตามประสาผู้ชาย
* **Ethan ↔ Ryan:** ขั้วตรงข้าม Ryan ชอบแหย่ให้ Ethan เสียอาการ ส่วน Ethan มักถอนหายใจและทำหน้าระอาใส่ความขี้เล่นของ Ryan

```
       [Jake]
      /      \
(คู่แข่งเพื่อนซี้) (เพื่อนสายลุย)
   /            \
[Ethan] -------- [Ryan]
   (สายแหย่ & สายเงียบ)
```

### ข้อมูลเฉพาะของตัวละคร

#### 1. Jake — กัปตันนักกีฬามาดมั่น (The Confident Athlete)
* **อายุ:** 21 ปี
* **บทบาทในค่าย:** หัวหน้ากิจกรรมกีฬาประจำค่าย (Staff Member)
* **บุคลิก:** มั่นใจในตัวเอง มีความเป็นผู้นำ อบอุ่น ปกป้องคนอื่นเก่ง แต่แอบหัวรั้นและชอบการแข่งขัน
* **รูปร่าง & ภาพลักษณ์:** ผิวสีแทน รูปร่างแบบนักกีฬา (Athletic) กล้ามเนื้อไหล่และแขนชัดเจน รอยยิ้มสว่างสดใส
* **สไตล์ความรัก:** รุกตรงๆ ชอบแสดงความเป็นเจ้าของและชวนทำกิจกรรมคู่ แต่จะเสียความมั่นใจและตึงเครียดทันทีเมื่อรู้สึกว่าตัวเองถูกมองข้าม
* **ปมในใจ:** กดดันจากการต้องเป็นผู้นำที่สมบูรณ์แบบตลอดเวลา และกลัวว่าจะไม่ดีพอ

#### 2. Ethan — หนุ่มสุขุมช่างสังเกต (The Stoic Observer)
* **อายุ:** 22 ปี
* **บทบาทในค่าย:** ผู้ดูแลอุปกรณ์และงานประสานงานเบื้องหลัง (Staff Member)
* **บุคลิก:** พูดน้อย สุขุม เป็นผู้ใหญ่ ช่างสังเกต และเก็บความรู้สึกเก่ง
* **รูปร่าง & ภาพลักษณ์:** ผิวขาว รูปร่างเพรียวแต่มีกล้ามเนื้อแน่น (Lean & Muscular) โครงหน้าคม แววตาคมกริบ
* **สไตล์ความรัก:** รักแบบค่อยเป็นค่อยไป (Slow-burn) แต่ลึกซึ้งและโรแมนติกมากเมื่ออยู่กันสองต่อสอง ให้ค่ากับความจริงใจและเกลียดการโกหกที่สุด
* **ปมในใจ:** มักซ่อนความต้องการของตัวเองไว้ข้างหลังคนอื่น และกลัวที่จะเปิดใจยอมรับว่าตัวเองต้องการความรัก

#### 3. Ryan — หนุ่มเจ้าเสน่ห์สายปั่น (The Magnetic Free Spirit)
* **อายุ:** 20 ปี
* **บทบาทในค่าย:** ผู้ช่วยไลฟ์การ์ดและตัวสร้างสีสันรอบกองไฟ (Camp Participant / Assistant)
* **บุคลิก:** ขี้เล่น พูดเก่ง สดใส มั่นใจในเสน่ห์ของตัวเอง ชวนแหกกฎ
* **รูปร่าง & ภาพลักษณ์:** รูปร่างสมส่วนมีกล้ามเนื้อแบบธรรมชาติ (Casual Muscular) ผมสีบลอนด์ประกายแดด รอยยิ้มเจ้าเล่ห์
* **สไตล์ความรัก:** รุกไว แตะเนื้อต้องตัวเก่ง ชอบหยอดและพาไปทำเรื่องตื่นเต้น แต่ลึกๆ ต้องการความจริงใจที่มากกว่าแค่ความสัมพันธ์ฉาบฉวย
* **ปมในใจ:** กลัวการผูกมัดและกลัวว่าจะถูกมองว่าเป็นแค่ความสัมพันธ์ชั่วคราวช่วงฤดูร้อน

## 7. ระบบความสัมพันธ์ (Relationship System)

### 1. ตัวแปรเชิงตัวเลข (Numeric Stats)
มี 2 ค่าหลักต่อตัวละคร (สเกล 0 ถึง 100, ซ่อนตัวเลขจากหน้าจอผู้เล่น):
* **Attraction (ความดึงดูด/ความปรารถนา):** วัดเคมีทางกายภาพ ความโรแมนติก และความหลงใหล
  * *เพิ่มขึ้นจาก:* การหยอดคำหวาน (Flirt), การสัมผัสใกล้ชิด, การสบตา, การเลือกอยู่ด้วยกัน
* **Trust (ความเชื่อใจ/ความจริงใจ):** วัดความมั่นคงทางอารมณ์ ความปลอดภัย และความจริงใจ
  * *เพิ่มขึ้นจาก:* การพูดความจริง, การเปิดใจแชร์เรื่องส่วนตัว, การรักษาสัญญา
  * *ลดลงจาก:* การถูกจับได้ว่าโกหก, การผิดนัด, การทำตัวลับๆ ล่อๆ

### 2. ลำดับสถานะความสัมพันธ์ (Relationship Status Progression)
เพื่อความชัดเจนในการประเมินบทสนทนาและ Jealousยี่ แต่ละตัวละครจะมีสถานะกำกับแบบ Deterministic:
1. `'casual_interest'` (ค่าเริ่มต้น): มีความสนใจเบื้องต้น ยังไม่มีข้อผูกมัด
2. `'romantic_interest'` (เมื่อ `Attraction >= 40` และ `Trust >= 30`): เริ่มมีเคมีและความรู้สึกพิเศษชัดเจน
3. `'mutually_acknowledged'` (เมื่อ `Attraction >= 60` และ `Trust >= 50` พร้อมผ่านฉากเปิดใจสองต่อสอง): รับรู้ความรู้สึกซึ่งกันและกันอย่างไม่เป็นทางการ
4. `'exclusive'` (เมื่อ `Attraction >= 75` และ `Trust >= 65` พร้อมยืนยันข้อตกลงผูกมัด): ตกลงคบหาหรือเลือกกันอย่างเป็นทางการ

### 3. เมทริกซ์ความสัมพันธ์ 4 รูปแบบ (The 4-Quadrant Matrix)

| สถานะ | High Trust ($\ge 50$) | Low Trust ($< 50$) |
| :--- | :--- | :--- |
| **High Attraction ($\ge 50$)** | **Secure Romance (รักมั่นคง):** หวานซึ้ง อบอุ่น มั่นใจในกันและกัน พร้อมเปิดเผยความรู้สึก | **Volatile Obsession (หลงใหลแต่ขี้ระแวง):** เคมีร้อนแรง หึงหวง ประชดประชัน อารมณ์แปรปรวน |
| **Low Attraction ($< 50$)** | **Solid Camaraderie (มิตรภาพแท้จริง):** เพื่อนสนิทที่ไว้ใจได้ ให้เกียรติซึ่งกันและกัน | **Distant Acquaintance (คนรู้จักที่ห่างเหิน):** เย็นชา ไม่สนใจบทสนทนา ไม่มีความผูกพัน |

### 4. ระบบความหึงหวงตามบริบท (Contextual Jealousy Model)
ความหึงไม่ใช่ตัวเลขสะสม แต่ถูกประเมินแบบเรียลไทม์ตามสถานการณ์:
$$\text{Jealousy Trigger} = (\text{Attraction} \ge 50) \land (\text{ผู้เล่นใกล้ชิด/หยอดคนอื่นในระยะที่เห็น}) \land (\text{RelationshipStatus} \ne \text{'exclusive'})$$

*หมายเหตุ: หากสถานะเป็น `exclusive` กับตัวละครนั้นแล้ว การที่ผู้เล่นไปหยอดคนอื่นจะไม่ใช่แค่ความหึงตามบริบท แต่จะกลายเป็นการผิดสัญญาและลด Trust ฮวบทันที*

**การแสดงออกตามระดับ Trust:**
* **High Trust ($\ge 50$):** แซวตรงๆ ถามอย่างเปิดเผยด้วยรอยยิ้มหรือแววตาหยอกล้อ (*"เห็นนะว่าเมื่อกี้แอบไปยืนคุยอะไรกันสองคนริมสะพาน?"*)
* **Low Trust ($< 50$):** ประชด สบตาด้วยความไม่พอใจ เก็บกด หรือเปิดฉากซักไซ้ด้วยอารมณ์ (*"อย่าให้ฉันต้องไปขัดจังหวะเกมอะไรที่นายกำลังเล่นอยู่เลยนะ"*)
* **Low Attraction ($< 50$):** ไม่เกิดความหึง มองเป็นเรื่องปกติหรือช่วยเพื่อนแซว

### 5. ระบบบันทึกความทรงจำการโกหก (Simple Lie Memory Flags)
ใช้ตัวแปร Boolean ตรงไปตรงมาเพื่อรอการเปิดโปงในอนาคต:
* `lied_about_midnight_lake: boolean`
* `promised_jake_first_dance: boolean`
* `lied_to_ethan_about_ryan: boolean`

## 8. ระบบตัวเลือกและลำดับความสำคัญ (Choice System & Routing Priority)
ตัวเลือกจะปรากฏประมาณ 1–2 ครั้งต่อฉาก (บางฉากจะไม่มีตัวเลือกเพื่อรักษาจังหวะการเล่าเรื่อง):

### ประเภทของตัวเลือก
1. **ตัวเลือกโทนบทสนทนา (Tone Choices):**
   * *Flirty (หยอด):* เพิ่มค่า `Attraction`
   * *Sincere (จริงใจ):* เพิ่มค่า `Trust`
   * *Teasing/Deflective (กวน/เบี่ยงประเด็น):* รักษาท่าที ไม่เพิ่มหรือลดค่าชัดเจน
2. **ตัวเลือกการกระทำและการเลือกข้าง (Action Choices):**
   * เลือกว่าจะไปช่วยใคร นั่งข้างใคร หรือลงแข่งคู่กับใคร ส่งผลต่อคะแนนความสัมพันธ์โดยตรงและเปิดทางสู่ฉากย่อย
3. **ตัวเลือกความจริง vs การโกหก (Deception Choices):**
   * เลือกว่าจะพูดความจริงหรือแต่งเรื่องโกหกเพื่อเอาตัวรอดจากการสับราง

### กฎลำดับความสำคัญของเส้นทางฉาก (Choice Routing Priority)
เพื่อให้ Scene Runner สามารถทำงานได้อย่างแม่นยำและไม่มีความคลุมเครือ:
1. **Priority 1 (Choice-Level Destination):** หากผู้เล่นเลือกตัวเลือกที่มีการระบุ `ChoiceOption.nextSceneId` ระบบจะเปลี่ยนฉากไปยัง `nextSceneId` ของตัวเลือกนั้นทันที
2. **Priority 2 (Scene-Level Fallback):** หากตัวเลือกที่เลือกไม่มี `nextSceneId` (หรือในฉากนั้นไม่มีตัวเลือกให้เลือก) ระบบจะเปลี่ยนฉากไปยัง `GameScene.nextSceneId`
3. **Priority 3 (Flow Conclusion):** หากไม่มีการระบุ `nextSceneId` ทั้งใน Choice และ GameScene ให้ถือว่าจบช่วงตอน (Episode Conclusion) และส่งต่อไปยังขั้นตอนประเมินผลตอนถัดไปหรือประเมิน Ending

## 10. ระบบเหตุการณ์และเงื่อนไขแบบ Declarative Data (Event & Condition System)

### สถาปัตยกรรมของเงื่อนไข (Declarative Condition Architecture)
เพื่อให้ข้อมูลทั้งหมดสามารถจัดเก็บเป็น **JSON Serializable** ได้อย่างสมบูรณ์ จึง **ห้ามใช้ Executable JavaScript Functions ในข้อมูลบทสนทนา**:
$$\text{Narrative Data (JSON)} \longrightarrow \text{Declarative Conditions} \longrightarrow \text{Scene Runner Evaluates} \longrightarrow \text{Game State Changes}$$

### โครงสร้างเงื่อนไขแบบ Declarative (Declarative Condition Schema)
```typescript
interface DeclarativeCondition {
  type: 'stat' | 'flag' | 'relationshipStatus';
  target?: 'jake' | 'ethan' | 'ryan'; // จำเป็นเมื่อ type === 'stat' หรือ 'relationshipStatus'
  statKey?: 'attraction' | 'trust';   // จำเป็นเมื่อ type === 'stat'
  flagKey?: string;                   // จำเป็นเมื่อ type === 'flag'
  operator: '==' | '!=' | '>' | '>=' | '<' | '<=';
  value: number | boolean | string;
}

interface ConditionalDialogueVariant {
  conditions: DeclarativeCondition[]; // ประเมินผลแบบ AND logic
  overrideText: string;
  overrideExpression?: string;
}
```

* **ตัวอย่างข้อมูลใน JSON:**
```json
{
  "conditions": [
    { "type": "stat", "target": "ethan", "statKey": "attraction", "operator": ">=", "value": 60 },
    { "type": "flag", "flagKey": "lied_to_ethan", "operator": "==", "value": false }
  ],
  "overrideText": "Ethan ยิ้มบางๆ พลางขยับตัวเข้ามาใกล้จนไหล่สัมผัสกัน",
  "overrideExpression": "warm_smile"
}
```

* **มินิอีเวนต์เดี่ยวสุดพิเศษ (Exclusive Mini-Events):** ปลดล็อกทันทีหลังจบฉากใหญ่หากเงื่อนไข Declarative ผ่านเกณฑ์ (เช่น `ryan.attraction >= 40`)

## 12. บทสรุปและฉากจบ 6 รูปแบบที่แน่นอน (Deterministic Ending Rules)
Scene Runner จะประเมินผลฉากจบใน Scene 4.6 ตามลำดับ Priority อย่างเคร่งครัดโดยอิงจาก GameState ล้วนๆ ปราศจากการตีความแบบคลุมเครือ:

```
[ประเมินฉากจบใน Scene 4.6]
       │
       ├─► 1. ตรวจสอบ Crash & Burn Ending (Primary Tie-Breaker)
       │      เงื่อนไข: Trust ของทั้ง 3 คน < 35 AND โกหกสะสม >= 2 จุด
       │
       ├─► 2. ตรวจสอบ Polyamorous Ending
       │      เงื่อนไข: Attraction >= 65 และ Trust >= 70 ครบทั้ง 3 คน AND โกหกสะสม == 0
       │
       ├─► 3. ตรวจสอบ Solo Endings (Jake / Ethan / Ryan)
       │      เงื่อนไข: Attraction >= 70, Trust >= 60, ไม่เคยโกหกคนนั้น, คะแนนรวมสูงสุด
       │
       ├─► 4. ตรวจสอบ Summer Fling Ending
       │      เงื่อนไข: มีอย่างน้อย 1 คนที่ Attraction >= 65 และ Trust อยู่ระหว่าง 40-59
       │
       └─► 5. Default Fallback: จากลากันในฐานะเพื่อนร่วมค่าย (Amicable Departure)
```

### รายละเอียดเกณฑ์ของแต่ละฉากจบ:
1. **Heartbreak / Crash & Burn Ending:**
   * *เกณฑ์:* `(jake.trust < 35 && ethan.trust < 35 && ryan.trust < 35)` **และ** มี Flag การโกหกเป็นจริงตั้งแต่ 2 จุดขึ้นไป (`countLies >= 2`)
   * *ผลลัพธ์:* ความจริงเรื่องการสับรางแตกกระจายรอบกองไฟ ทั้ง 3 คนหันมาร่วมมือกันบอกลา และตัวเอกต้องเดินทางกลับบ้านคนเดียว
2. **Polyamorous Ending:**
   * *เกณฑ์:* `(jake.attraction >= 65 && ethan.attraction >= 65 && ryan.attraction >= 65)` **และ** `(jake.trust >= 70 && ethan.trust >= 70 && ryan.trust >= 70)` **และ** ไม่มีการโกหกแม้แต่จุดเดียว (`countLies === 0`)
   * *ผลลัพธ์:* ด้วยความจริงใจและการเปิดเผยตั้งแต่ต้น ทั้ง 4 คนตกลงพัฒนาความสัมพันธ์แบบเปิดร่วมกันอย่างลึกซึ้ง
3. **Jake Solo Ending:**
   * *เกณฑ์:* `jake.attraction >= 70 && jake.trust >= 60 && !flags.lied_to_jake` **และ** `(jake.attraction + jake.trust)` สูงกว่าคะแนนรวมของ Ethan และ Ryan
   * *ผลลัพธ์:* ความรักที่เปิดเผยและมั่นคงกับกัปตันหนุ่ม พร้อมแผนนัดพบกันต่อหลังจบค่าย
4. **Ethan Solo Ending:**
   * *เกณฑ์:* `ethan.attraction >= 70 && ethan.trust >= 60 && !flags.lied_to_ethan` **และ** `(ethan.attraction + ethan.trust)` สูงกว่าคะแนนรวมของ Jake และ Ryan
   * *ผลลัพธ์:* Ethan สารภาพความรู้สึกอย่างลึกซึ้งและจริงจังใต้แสงดาวในจุดลับริมทะเลสาบ
5. **Ryan Solo Ending:**
   * *เกณฑ์:* `ryan.attraction >= 70 && ryan.trust >= 60 && !flags.lied_to_ryan` **และ** `(ryan.attraction + ryan.trust)` สูงกว่าคะแนนรวมของ Jake และ Ethan
   * *ผลลัพธ์:* Ryan ละทิ้งท่าทีเล่นๆ และขอสร้างความสัมพันธ์จริงจังระยะยาว
6. **Summer Fling Ending:**
   * *เกณฑ์:* มีตัวละครอย่างน้อย 1 คนที่ `attraction >= 65` และ `trust` อยู่ระหว่าง `40 ถึง 59` (หรือไม่ผ่านเกณฑ์ Solo Ending และไม่เข้าเงื่อนไข Crash & Burn)
   * *ผลลัพธ์:* จูบลาอันแสนหวานและอบอุ่น จดจำค่ายนี้เป็นความทรงจำฤดูร้อนที่สวยงามโดยไม่มีข้อผูกมัดระยะยาว

* **ฉากจบ:** รองรับครบทั้ง 6 Ending Archetypes อย่างสมบูรณ์
* **เวลาในการเล่น:** ประมาณ 1.5 – 2.5 ชั่วโมงต่อ 1 รอบการเล่น

## 19. สถาปัตยกรรมทางเทคนิคและการแบ่งขอบเขตหน้าที่ (Technical Architecture & Layer Boundaries)

### การแบ่งขอบเขตหน้าที่ (Architecture Boundaries)
เพื่อให้ระบบสะอาด ดูแลรักษาง่าย และไม่มีการซ้ำซ้อน:
* **React 19:** รับผิดชอบเฉพาะส่วนการแสดงผล UI, กล่องบทสนทนา, ตัวเลือก (Choices), เมนูตั้งค่า, หน้า Save/Load, และหน้า Relationship Profile
* **Zustand:** รับผิดชอบจัดการ Client-side GameState, ค่าสถิติความสัมพันธ์, รายการ Flags, และ Session State ในหน่วยความจำ
* **Scene Runner (TypeScript):** เป็นหัวใจของ Gameplay รับผิดชอบการรันตามลำดับฉาก, Choice Priority Routing, การ Evaluate Declarative Conditions, การกลายพันธุ์ State (State Mutation), และการคำนวณ Ending
* **PixiJS v8:** รับผิดชอบเฉพาะการเรนเดอร์กราฟิก 2D, พื้นหลัง, สไปรต์ตัวละคร, Event CG, เอฟเฟกต์แสง และการซูม/แพนมุมกล้องแบบภาพยนตร์
* **Tauri v2 (Rust Backend):** รับผิดชอบเฉพาะระดับ Infrastructure เช่น Native Desktop Window Management, Native File I/O (บันทึก/โหลดไฟล์เซฟลงเครื่อง), และ Desktop Packaging **(ห้ามย้าย Gameplay หรือ Narrative Logic ไปไว้ที่ Rust)**

### กลยุทธ์เรนเดอร์ WebGPU พร้อม WebGL Fallback
* **Primary Renderer:** PixiJS v8 กำหนดให้ใช้ **WebGPU Renderer** เป็นแกนหลักเพื่อประสิทธิภาพสูงสุด
* **Fallback Strategy:** PixiJS v8 มีระบบ Feature Detection ในตัว หากตรวจพบว่าฮาร์ดแวร์หรือเบราว์เซอร์ไม่รองรับ WebGPU ระบบจะสลับไปใช้ **WebGL 2 Renderer** โดยอัตโนมัติอย่างไร้รอยต่อ

### แผนภาพสถาปัตยกรรม (Architecture Diagram)

```
|            (Rust Backend: Native File I/O & OS Window)        |
+---------------------------------------------------------------+

+---------------------------------------------------------------+

|       (Dialogue Box, Menus, Flowchart Tree, Profile Screen)   |
+---------------------------------------------------------------+
           │                                       ▲
           ▼                                       │
+--------------------+                   +--------------------+
|   Zustand Stores   |◄─────────────────►|    Scene Runner    |
| (GameState & Flags)|                   | (Narrative Engine) |
+--------------------+                   +--------------------+
           │                                       │
           ▼                                       ▼
+--------------------+                   +--------------------+
| PixiJS v8 Viewport |                   |   Audio Manager    |
| (WebGPU / WebGL)   |                   |    (Howler.js)     |

```

## 20. โครงสร้างข้อมูลและบทสนทนา (Content & Data Structure)

### 1. โครงสร้างสถานะเกม (Game State Schema)
```typescript
export type RelationshipStatus = 
  | 'casual_interest' 
  | 'romantic_interest' 
  | 'mutually_acknowledged' 
  | 'exclusive';

export interface CharacterState {
  attraction: number; // 0 ถึง 100
  trust: number;      // 0 ถึง 100
  status: RelationshipStatus;
}

export interface GameState {
  currentSceneId: string;
  protagonistName: string;
  characters: {
    jake: CharacterState;
    ethan: CharacterState;
    ryan: CharacterState;
  };
  flags: Record<string, boolean>; // e.g. "lied_about_midnight_lake": true
  history: string[];              // รายการ Scene ID ที่เคยเล่นผ่านมาแล้ว (สำหรับ Flowchart)
}
```

### 2. โครงสร้างเงื่อนไขแบบ Declarative (Condition Schema)
```typescript
export interface DeclarativeCondition {
  type: 'stat' | 'flag' | 'relationshipStatus';
  target?: 'jake' | 'ethan' | 'ryan';
  statKey?: 'attraction' | 'trust';
  flagKey?: string;
  operator: '==' | '!=' | '>' | '>=' | '<' | '<=';
  value: number | boolean | string;
}

export interface ConditionalDialogueVariant {
  conditions: DeclarativeCondition[];
  overrideText: string;
  overrideExpression?: string;
}
```

### 3. โครงสร้างฉากและตัวเลือก (Scene Definition Schema)
```typescript
export interface ChoiceOption {
  id: string;
  text: string;
  category: 'tone' | 'action' | 'deception';
  consequences: {
    targetCharacter?: 'jake' | 'ethan' | 'ryan';
    attractionDelta?: number;
    trustDelta?: number;
    newStatus?: RelationshipStatus;
    setFlags?: Record<string, boolean>;
  };
  nextSceneId?: string; // ถ้ามี จะมี Priority เหนือ GameScene.nextSceneId
}

export interface DialogueLine {
  id: string;
  speaker: 'protagonist' | 'jake' | 'ethan' | 'ryan' | 'narrator';
  text: string;
  spriteState?: {
    character: 'jake' | 'ethan' | 'ryan';
    expression: string;
    position: 'left' | 'center' | 'right';
  };
  cameraEffect?: 'zoom_in' | 'pan_left' | 'shake' | 'default';
  conditionalVariant?: ConditionalDialogueVariant;
}

export interface GameScene {
  id: string;
  episode: 1 | 2 | 3 | 4;
  day: 1 | 2 | 3 | 4 | 5;
  backgroundId: string;
  bgmId?: string;
  dialogue: DialogueLine[];
  choices?: ChoiceOption[];
  nextSceneId?: string; // Fallback เมื่อไม่มี Choice-level destination
}
```

## 21. ความเสี่ยงในการพัฒนาและแนวทางแก้ไข (Implementation Risks)

| ความเสี่ยง | ระดับผลกระทบ | แนวทางป้องกันและแก้ไข |
| :--- | :--- | :--- |
| **PixiJS กับ React ซิงก์ State ไม่ตรงกัน** | สูง | ให้ PixiJS ทำหน้าที่เป็น Stateless Renderer ที่รับคำสั่งผ่าน Event/Store จาก Zustand เป็นทางเดียว |
| **ความเข้ากันได้ของ WebGPU บนเครื่องผู้เล่น** | ปานกลาง | ใช้ความสามารถ Auto-fallback ของ PixiJS v8 สลับไป WebGL อัตโนมัติเมื่อ WebGPU ใช้งานไม่ได้ |
| **บทสนทนาขนาดใหญ่ดูแลยาก** | ปานกลาง | แยกไฟล์บทสนทนาออกเป็นราย Episode (เช่น `episode1.json`, `episode2.json`) ที่มี TypeScript Schema ตรวจสอบความถูกต้อง |
| **ตรรกะการจับโกหกซับซ้อนจนผู้เล่นสับสน** | ปานกลาง | ใช้ Flag แบบ Boolean ธรรมดา (`lied_about_X`) และกำหนดจุดเช็กบิลความลับเฉพาะใน Episode 3 และ 4 เท่านั้น |

## 22. แผนการพัฒนา (Development Milestones)

### ระยะที่ 1: แกนหลักและระบบทดสอบ (สัปดาห์ที่ 1–3)
* ติดตั้งโครงโปรเจกต์ Tauri v2 + React 19 + Vite + TypeScript + PixiJS v8 (WebGPU)
* สร้าง Zustand store, Scene Runner พร้อมระบบประเมิน Declarative Condition
* สร้างระบบกล่องข้อความพร้อมเอฟเฟกต์พิมพ์ดีด และตัวเรนเดอร์สไปรต์พื้นฐานบน PixiJS
* ทำเดโมทดสอบ 2 ฉากเพื่อตรวจการเลือกตัวเลือก, Choice Priority Routing, และ State updates

### ระยะที่ 2: เนื้อหา Episode 1 และระบบสนับสนุน (สัปดาห์ที่ 4–6)
* ประกอบ Episode 1 (Day 1: Scene 1.1 ถึง 1.5 รวม 5 ฉาก)
* พัฒนาระบบบันทึก/โหลดเกม (Save/Load) ผ่าน Tauri Native File I/O
* ทำหน้าต่างสถานะความสัมพันธ์ (Relationship Profile Screen) และระบบเสียงผ่าน Howler.js

### ระยะที่ 3: เนื้อหา Episode 2 & 3 และระบบดราม่า (สัปดาห์ที่ 7–10)
* ประกอบ Episode 2 (Day 2: 4 ฉาก, Day 3: 3 ฉาก รวม 7 ฉาก)
* ประกอบ Episode 3 (Day 4: 6 ฉาก รวมเรื่องความลับและ Flag การโกหก)
* นำเข้าสไปรต์ตัวละครและฉากหลังครบทุกช่วงเวลา พร้อมระบบ Exclusive Mini-Events

### ระยะที่ 4: Episode 4 ฉากจบ และความสะดวกในการเล่นซ้ำ (สัปดาห์ที่ 11–13)
* ประกอบ Episode 4 (Day 5: 6 ฉาก รวมคืนรอบกองไฟและการเปิดโปง)
* ติดตั้งระบบประเมินผลฉากจบ 6 เส้นทางแบบ Deterministic
* พัฒนาระบบ Scene Flowchart (24 ฉาก) และระบบ Gallery

### ระยะที่ 5: ขัดเกลา ทดสอบ และปล่อยตัวเกม (สัปดาห์ที่ 14–16)
* ปรับสมดุลตัวเลข Attraction และ Trust จากการทดลองเล่นจริง
* ปรับแต่งแอนิเมชันการเปลี่ยนฉากและเสียงประกอบ
* ตรวจสอบความเข้ากันได้ของ WebGPU / WebGL Fallback และ Build ผ่าน Tauri Desktop และ Web Demo
